# Installed runtime and Python prerequisites

This file is shipped with the recorder Skill. Developer architecture and contribution documents are maintained in the source repository and are not required to read this installed Skill.

## Primary workflow

The selected main path is DSH Host → bundled Python CLI → recorder card. The optional Client card calls the same Host service through Typert Remote and owns no BLE connection; it is not a prerequisite for Host loading or CLI experiments. The current workspace build registers eight recorder tools; full hardware and transcription acceptance is separate.

Validate the standalone CLI first on the intended Host machine: use the bundled pinned sources and record Python/Bleak, OS, Bluetooth adapter/driver, permissions, and the actual script arguments. Verify scan/status/list and import/play one disposable recording, then recording controls and failure recovery. Keep standalone CLI results separate from later DSH tool acceptance.

## Execution locations

The Client card calls Host Remote. The Host runs Python and Bluetooth on the DSH Host machine, which may differ from the browser machine. A remote Host does not automatically have access to the browser's Bluetooth hardware.

The Host machine must have working Bluetooth hardware and permissions and be able to connect to the intended card. Use one BLE owner at a time. Disconnect external browser direct-BLE sessions, phone apps and other CLI sessions before device access; the current card itself owns no BLE connection. Do not combine file import and realtime capture.

The Host supports a persistent connection worker plus a legacy one-shot CLI path. `recorder_connect` reconnects the saved card or scans for a unique device; multiple candidates require user selection. The worker owns the BLE session until disconnect, failure, cancellation or Host disposal. Device calls serialize on it, and its whole lifetime holds the module-wide BLE queue. Other Node Hosts and external clients are not coordinated. `connectionState` reads memory only, while `status` performs BLE I/O. The icon polls only connectionState. Client unmount cancels its pending calls and polling; an already connected shared session remains owned by Host. Standalone transcription runs outside the BLE queue.

The manager accepts cancellation signals, rejects cancelled queued calls without spawning, and waits for active subprocess exit before releasing the device queue. Its cleanup is registered with `ctx.effect`. Windows local tests and real DSH isolated-profile disable/re-enable passed, including termination of an active synthetic subprocess. BLE cancellation remains unverified.

## Bundled CLI adapter

The [adapter](../../runtime/recorder_cli.py) loads bundled `vendor/upstream/` sources from upstream commit `de42d1fbf19fc92064ac4688f71f42730c82267f`. It verifies SHA-256 of `tools/qs668-bringup.py` and `tools/qs668_protocol.py` (normalizing CRLF to LF) before import. Unsupported/missing source fails before any BLE operation. The scripts, requirements, full MIT license and provenance are shipped in the package. No clone is needed. `repoRoot` is an optional developer override; missing or empty uses bundled sources. The device-source hashes are unchanged, and transcription has its own pinned hash. It does not download or modify upstream scripts. This path has been tested with Python 3.12.7 and Bleak 3.0.2 on Windows.

Install Python 3.11+ on the Host and run `python -m pip install bleak requests` with the same interpreter configured in `python`. Missing/broken dependencies report that interpreter and installation command; no dependencies are installed automatically. From the installed plugin directory:

```text
python -B runtime/recorder_cli.py --check-deps
python -B runtime/recorder_cli.py -- --help
python -B runtime/recorder_cli.py -- --scan
python -B runtime/recorder_cli.py -- --address <device> --list
```

The adapter requires `2-18` status `0` for a complete list and rejects malformed list entry counts. No-response/partial-list timeouts and invalid end states fail; they block another list/record command on that session. Recording start/save/pause/resume require the corresponding `3-2/4/6/8` response with status `1`; hardware events or a state response are not substitutes. An unconfirmed command may already have executed: inspect state, reconnect, and make an explicit recovery decision instead of blindly retrying.

Device operations have a default 180-second asynchronous operation timeout, adjustable with adapter `--timeout` before the `--` separator. List response limits are 4 seconds initially, 1.2 seconds of idle time after data, and 30 seconds overall; recording acknowledgement waits up to 3 seconds. Cleanup attempts are limited to 5 seconds per session and cleanup failure is reported. These are adapter policies, not firmware guarantees. Exit codes include 1 for validation/unconfirmed results, 124 for operation timeout, and 130 for keyboard cancellation; scan exit 0 can still mean no device. Blocking external subprocess work such as transcription is outside the asynchronous BLE timeout guarantee.

The internal Host device methods use this adapter. Standalone transcription uses the same adapter without opening a BLE session. The adapter stages imports privately and publishes without overwriting existing audio. RIFF/WAVE PCM structure and frame completeness are checked before publication; other formats remain unconfirmed and fail. Source-content integrity and every device status field still require independent evidence. Source pinning and confirmation checks do not establish full M2a/M2b acceptance.

## Current Host wrapper

These fields are read by the current JavaScript wrapper. They are declared by the plugin Config schema, verified during isolated DSH Host loading. Desktop settings UI remains unverified.

| Field | Default | Meaning |
|---|---|---|
| `python` | `python` | Interpreter available on the Host |
| `repoRoot` | Package `vendor/upstream/` | Optional developer source override at the same pinned revision; omitted/empty uses bundled sources. Not a data directory |
| `dataDir` | Host user home `~/.dsh-recorder-card` | Writable data root for audio, corpus, device cache and optional ASR `.env`; independent of source location |
| `deviceAddress` | None | Optional fallback. recorder_connect discovers and saves a card; legacy one-shot device operations require a saved/configured address |
| `outDir` | `archive/audio` | Single-file import destination; converted to an absolute path under `dataDir` |
| `cliTimeoutMs` | `190000` | Positive integer Host watchdog in milliseconds, excluding queue time. Both Python entry points receive `(cliTimeoutMs - min(10000, cliTimeoutMs / 2)) / 1000` seconds for each BLE operation; the remainder allows startup/cleanup. Default remains 180 seconds internally. Released 0.5.0 did not propagate this setting |

Internal method signatures are `scan/status/list/recordState({ signal }?)`, `record(action, { signal }?)`, `importFirst(outDir?, transcribeFlag?, { signal }?)`, and `transcribe(file, { force?, signal? }?)`. Recording actions are restricted to `start`, `pause`, `resume`, and `save`. These are internal service signatures; the eight Agent tools are defined in the [tool adapter](../../runtime/tools.js). Connection management returns structured connection states. Except for connection management, import and transcription, successful device operations return `{ code, out, err }`; import uses the separate stage result described below. Failures distinguish `CliSpawnError`, `CliExitError`, `AbortError`, `TimeoutError`, `OutputLimitError`, and `CleanupError`. Exit failures retain output/exit details; zero exit alone does not prove every status field or imported file is valid.

The one-shot Host runner caps captured stdout/stderr at 8 MiB total. The persistent worker caps each JSON response buffer at 8 MiB and retains only the last 4096 characters of diagnostics. Cancellation of a dispatched request, timeout and output overflow terminate the process tree using Windows `taskkill /T /F`, or a POSIX process group (SIGTERM followed by SIGKILL after one second). The POSIX path is not validated. If termination fails while the process remains open, the call reports `CleanupError`, disposal reports incomplete cleanup, and the device queue stays blocked until actual exit. Normal Python completion attempts BLE disconnect; forced termination cannot guarantee Python finally blocks or firmware state. Inspect device state and any partial file before recovery; cancellation is not a recording stop/save command, and commands are never automatically retried.

This package includes the adapter, JavaScript process manager and pinned Python CLI sources. Python/Bleak/requests and optional ffmpeg are system dependencies, not bundled binaries. Upstream protocol documentation is not included. No dependency installer or credential bootstrap runs automatically.

Subprocesses inherit the Host environment with Python UTF-8 I/O and bytecode writing disabled. `transcriptionProvider` defaults to `dsh`: the injectable recorder service resolves the Host's selected recognizer with `speechToText.resolve({ audio })`, then calls `transcribe(spec, signal)` directly.

Check package availability, profile composition and recognizer readiness separately:

1. The Host must be able to load `@deepseek-ai/dsh-experimental-speech-to-text` and a compatible recognizer provider. These are not bundled with this plugin, but DSH may already include them; install compatible packages separately only when absent.
2. The active profile must mount the `speechToText` service and register the selected recognizer. Package installation alone does not activate them. The inspected Windows DSH Desktop 0.2.0-rc.2 includes the speech packages, but its default `dsh-base` / `dsh-web-app` bundles do not reference them. Our test used an additional profile patch. Verify the actual version and profile instead of assuming default mounting.
3. The tested local provider is `@deepseek-ai/dsh-experimental-speech-to-text-sensevoice`. It needs valid provider configuration, an absolute writable Host `dataRoot`, and prepared models. Existing model files may be reused through its configuration; do not assume installing the package downloads or prepares them. Local inference needs no cloud credentials.

`@deepseek-ai/dsh-experimental-api-speech-to-text` exposes the official speech Remote interface, including preparation controls for the corresponding UI. It is not required by the recorder's direct Host calls; configure it when using features that depend on that interface. Do not treat it or SenseVoice as mandatory for every possible `speechToText` provider.

Only an absent service falls back to `doubao`; an existing service's resolution, readiness, inference or cancellation failure never triggers fallback. Explicit `doubao` uses the pinned CLI, Host environment variables and `dataDir/.env`, and uploads audio. Do not initiate transcription without user intent.

Standalone transcription returns `{ status: succeeded, provider, recognizer, path, audioPath, audioSha256, reused, fallbackReason? }`, not a process result. Its stable failure code is `RECORDER_TRANSCRIPTION_FAILED` (Remote: `recorder/transcription-failed`). Audio remains available after failure. Import completes before invoking this same pipeline; a persistent session remains owned by Host and preserves independent cleanup warnings. DSH's plain `Transcript` has no diarization or segment times: Markdown labels the default speaker and filename-derived start time explicitly, with an unknown timezone.

Archives under `dataDir/archive/corpus/` use content SHA-256 plus provider/recognizer/language/schema identity, verify body integrity before reuse, and atomically publish without replacing existing files. `force` creates a new result without deleting the old one. Empty recognition is an error. Current input is canonical 44-byte-header, 16 kHz mono PCM16 WAV up to 64 MiB; the selected recognizer may impose a lower limit. There is no automatic splitting/resampling. A recognizer model changed under the same ID requires `force` to regenerate an archive.

## Cache association fixes in 0.3.1

Version 0.3.1 rechecks the current audio fingerprint immediately before returning a cache hit or publishing a new archive. Changed, truncated or removed files fail without a stale success. A same-content file at another path reuses recognition text but publishes a separate Markdown with the current `audio` path and title; `reused: true` does not require the Markdown path to stay the same. Existing exact-path archives take precedence. Original archives remain unchanged. `transcription_source_audio` and `recorded_at_source_audio` preserve historical recognition and filename-derived timing provenance; they may no longer exist and are not active audio references. Renaming does not shift transcript times. Validation applies at return/publication time, not to future external writes. These fixes require 0.3.1 or later; 0.3.0 is affected.

## Safe import and separate transcription results

The workspace adds `recorder_import.filename` and `importFile(filename, outDir?, transcribe?, options?)` on the shared Service. `importFirst` remains compatible. Selection is exact against a confirmed list; missing, ambiguous or stem-only names never silently select a different file. Names cannot contain paths, control characters or commas. The one-shot Host passes a single `--filename=<name>` argument, never `--import-all` together with it. The persistent worker selects and imports on its existing Session; the Service runs optional transcription afterward without handing the card to another process. Each call imports one file, so an Agent can process an authorized selection sequentially and stop on failure.

Transfer failures have stable codes `RECORDER_DEVICE_DISCONNECTED` / `RECORDER_TRANSFER_INTERRUPTED` (Remote `recorder/device-disconnected` / `recorder/transfer-interrupted`). The latter does not assert a physical drop. The adapter saves the primary transfer error in its private report; the worker sends it through its response. Unconfirmed cleanup takes priority and keeps the primary diagnostic. Cancellation and overall deadlines remain separate error codes. Check the device, reconnect and explicitly retry the failed file from the beginning; no automatic reconnection or byte resume is implemented. RIFF validation failures are not reported as successful transfers. Do not retry already imported audio just because transcription failed.

The adapter runs the pinned upstream import in a fresh `.recorder-import-*` directory beneath the destination. After the upstream function confirms transfer completion, it validates RIFF/WAVE PCM structure, computes SHA-256, flushes the file, and publishes it using an atomic hard link. RIFF length must equal file length, every chunk including padding must fit, PCM format fields must agree, and sample data must contain whole non-empty frames. Missing/duplicate format or data chunks, truncated/unsupported encodings fail as integrity unconfirmed before publication or transcription. Existing names (including a file created concurrently) are never replaced; a UUID suffix is chosen on conflict. The filesystem must support hard links; failure does not fall back to an overwriting copy/rename. Normal failure/cancellation removes staging; forced process termination may leave an ignored-looking staging directory, which is not a completed import. Already published audio remains intact. Verification is limited to the supported PCM container and sample frames, not a source checksum or proof of absence of all transmission corruption; M3 hardware acceptance remains pending.

`recorder_import` now returns `{ status, import, transcription, cleanup }`. `import` contains `status: succeeded`, the actual absolute `path`, `bytes`, `sha256`, and `integrity` (verified PCM format, channels, sample rate, bit depth and frame count). Transcription is `not-requested`, `succeeded`, or `failed`. On transcription failure, overall `status` is `partial`, with an independent `transcription.error` and `transcription.retry` naming `recorder_transcribe` with the retained audio path. Retry transcription only, not import. DSH dispatch may have `isError: false` for this successfully reported partial workflow: callers must inspect the explicit workflow and stage statuses. Import/validation failures remain DSH errors, and cancellation must not be reported as workflow success.

Cleanup is independently `succeeded`, `not-needed`, `retained` (persistent Host ownership), or `unconfirmed`, with structured errors. Every disconnect attempt is observed, including the first call inside upstream code. A failed, timed-out or cancelled attempt remains unconfirmed even if upstream clears its client reference and a later call returns without doing anything. A pending/missing cleanup result is unconfirmed. Either transcription failure or unconfirmed cleanup makes the workflow `partial`; both problems survive when they occur together. Do not assume the device was released or start another BLE operation while cleanup is unconfirmed.

The Host reads a private version-2 JSON import/cleanup report written atomically by the adapter through `--result-file`; missing or invalid reports fail. The shared recorder service imports with CLI transcription disabled, then runs the DSH/default-or-Doubao pipeline described above. The lower-level Python adapter retains its separately tested 120-second CLI post-import transcription option for direct callers; that option does not implement DSH STT. ASR credentials are not needed for scan/import. Direct CLI transcription failure exits nonzero and preserves imported audio. Complete hardware recovery remains unaccepted.

## Output and completion

### Transfer diagnostics

Persistent requests and one-shot imports may return optional `diagnostics` (version 1). Remote failures carry it in `error.details.diagnostics`; Agent errors append a bounded `recorder diagnostics: {...}` JSON object while retaining the stable error code. DSH cancellation may replace the visible error, so the shared Host service atomically saves the latest diagnosed operation as `{ recordedAt, diagnostics }` in `dataDir/recorder-diagnostics.json`. Later diagnosed operations replace it; collect it before another operation if needed. Storage failure warns without replacing the primary operation result. It contains no audio, payload, filename, path, address or transcript; keep runtime files out of source control.

`phase`/`failedPhase` distinguish `queued`, `starting`, `scan`, `connect`, `status`, `list`, `importWrite` (awaiting the existing write call), `transfer`, `validate`, `publish`, `cleanup`, and terminal `done`/`failed`. Missing timing fields mean not observed, not zero. `outcome` and `cleanup` describe device work independently of optional later transcription. `queueMs` measures Host queue wait; `elapsedMs` and stage `*Ms` use monotonic timing. Nested stages overlap: do not add them to obtain a total. `firstFrameMs`, `firstDataMs`, `lastDataMs`, `endFrameMs` are offsets from operation start, not wall-clock timestamps. `endCode` is the observed completion-frame byte, not an integrity verdict.

`bytesReceived` counts parsed 2-4 frame payload bytes and `dataFrames` counts those frames. `attempts` counts import writes observed by the adapter; counters aggregate any attempts made by pinned upstream behavior. They do not represent unique bytes or a resumable offset. The device list size can describe compressed data while transfer produces PCM, so never divide these counts by list size for a percentage. A completion frame still requires existing PCM validation before publication.

Internal progress snapshots are sampled about once per second, without a Client progress stream. `snapshotAgeMs` reports the age since Host received the snapshot (worker) or the report was written (one-shot). Forced termination can miss the last frames and leaves cleanup unconfirmed; a missing snapshot gives Host-only phase/counters, not proof no device action occurred. Queued cancellation with `cleanup: not-needed` is distinct: that request was never dispatched. Standalone one-shot scan/status/list/record and ASR do not currently expose these diagnostics. There is no automatic reconnection or byte resume.

Version 0.6.0 adds `frameIntervalSamples`, `frameIntervalMedianMs`, `frameIntervalP95Ms`, `frameIntervalMaxMs`, `stalls`, `dataIdleMs` and `idleTimeoutMs`. Intervals use the latest 32 parsed data-frame arrival gaps, not radio connection intervals; p95 uses nearest rank. A resumed gap exceeding `max(5s, 3 * previous median)` increments the cumulative stall count. Current silence appears in `dataIdleMs` until the next frame or termination; a missing next frame cannot increment a completed-gap counter. No samples means interval statistics are absent. Import attempts reset the last-frame timestamp to avoid counting filename negotiation time, while the bounded interval window and stall count remain per operation.

The pinned importer still assembles frames and confirms completion. During that one serialized import the adapter sets its runtime `IMPORT_IDLE_S` to `min(20s, max(12s, 3 * median))`, then restores the setting and observer on success, failure or cancellation. Bundled sources/hashes are unchanged. The actual previous import idle timeout was 12 seconds; 1.2 seconds applies to the file list. A 5-second floor would reduce existing tolerance. Python deadlines now follow the Host setting and report TimeoutError; Host forced termination remains the outer watchdog. For example, `cliTimeoutMs: 610000` allows a 600-second Python operation, excluding the startup/cleanup reserve. Very small watchdogs may still kill Python before cleanup finishes. This does not increase BLE throughput.

After disconnect, the adapter checks the original client reference because upstream clears Session.client in finally. If a transfer was interrupted, normal Python cleanup additionally waits up to 3 seconds for the same address to advertise, all within the existing 5-second cleanup bound. A still-connected client, missing advertisement, scanner error or cleanup timeout stays unconfirmed; later no-op disconnects cannot erase that result. Missing advertising does not prove a live connection, and advertising does not prove GATT readiness. Wake or power-cycle as needed, then explicitly reconnect; do not continue a batch automatically while release/readiness is unconfirmed. Forced termination cannot execute this recovery check reliably. Duration-based hard rejection remains pending: `duration_or_time` is not yet a confirmed seconds field, and one measured transfer rate is not a safe universal bound.

### Import budget preflight

Version 0.6.0 opt-in Host precheck: `recorder_import` and the `importFirst` / `importFile` Remote options accept `preflight: { expectedBytes, bytesPerSecond }`, both positive safe integers. Supply estimated exported audio bytes and a user-approved reference payload rate for the selected recording/link. Card-list size is compressed storage; the list time field is not a verified duration. No automatic conversion, speed learning or live speed probe is performed. Standalone Python CLI calls bypass this Host check.

For a confirmed standard 44-byte-header, 16 kHz mono PCM16 output lasting 16 seconds, `44 + 16000 * 2 * 16 = 512044` bytes. This format/duration must be known for the selected recording. Example tool arguments:

```json
{"filename":"exact name from recorder_list","preflight":{"expectedBytes":512044,"bytesPerSecond":1000}}
```

Required operation time is `ceil(expectedBytes / bytesPerSecond * 1.25 + 15)` seconds: estimated transfer plus 25% margin and 15 seconds of setup allowance. These margins are policy, not measured overhead. Compare with `(cliTimeoutMs - min(10000, cliTimeoutMs / 2)) / 1000`, the Python budget for both import paths. The example needs 656 seconds versus the default 180, returns `RECORDER_IMPORT_BUDGET_EXCEEDED` (Remote `recorder/import-budget-exceeded`), and suggests `cliTimeoutMs: 666000`. If that suggestion exceeds the supported Host timeout range, the message asks for a smaller recording or a new link measurement instead.

Rejection starts no import, preserves an existing persistent connection and leaves the queue usable; diagnostics show zero attempts and `cleanup: not-needed`. Passing is not a completion guarantee. Omitting preflight preserves existing behavior; after rejection, obtain an explicit recovery decision before changing estimates/configuration or omitting the check. No automatic retry, timeout adjustment, splitting or byte resume is added.

### Output paths

Prefer explicit absolute input/output paths during verification. Audio defaults to `dataDir/archive/audio/`; transcription defaults to `dataDir/archive/corpus/`. Relative tool paths resolve under `dataDir`, never `repoRoot`. Python bytecode writing is disabled. Data paths inside CLI sources are rejected by the Host. Existing users: relative paths previously resolved under repoRoot. Old files are left untouched; use absolute audio paths or copy them to the new data directory. Do not set dataDir to the CLI source tree. No files are migrated automatically. Report the actual output path. A standalone CLI success does not prove DSH Agent tools or browser import are working.

Preserve imported audio when transcription fails. Do not reuse a transcript solely because a filename matches; require valid text and a matching `audio_sha256` when the chosen implementation supports reuse. Keep audio, transcripts, credentials, and device-address caches out of version control at the actual output location.

## Client Remote cancellation and retry

Connection cleanup failures use the sticky connection state `cleanup-unconfirmed` plus a diagnostic message, including failures during idle retirement and abnormal worker exits. This differs from an import's `cleanup.status: unconfirmed`. Process closure and repeated disconnect calls do not erase it. Device requests already queued before the warning fail with `CleanupError` without accessing BLE; each previously uninformed service instance also receives that error on its first device request. Tell the user to check the device before explicitly retrying; never retry automatically. The runtime delivers the warning but cannot verify the physical check. A newly confirmed connection clears the shared notice, while failed instances retain their own terminal evidence. Standalone transcription is unaffected.

The 0.5.0 Client contract has twelve cancellable Remote methods, including importFile and connect/disconnect/connectionState; released 0.4.0 has eleven. Connect is cancellable; failed/cancelled dispatched device operations retire the session before retry. Cancelling an unsent queued request returns AbortError immediately without stopping the active operation. An unexpected drop interrupts idle or active work, and Host closes stdin so the Python reader can exit. The global BLE queue is released only after process/pipe closure, with termination escalation if the worker does not exit within ten seconds. Forced termination leaves physical connection release unconfirmed. A successful import on a persistent connection reports `cleanup.status: retained`: the Host intentionally keeps ownership, rather than claiming release. Transcription failures preserve audio and independent cleanup warnings. The old browser list retry rules apply only to the retired fixture.

## Device selection

The icon auto-connects the saved device or scans on first use. One candidate connects and is saved; multiple candidates are offered in the conversation and must be selected explicitly before recorder_connect(address). Empty address clears the saved selection and scans afresh. Right-click / Shift+F10 exposes disconnect and switch. `getDevice` and `saveDevice` Remote methods remain available for integrations, but the toolbar has no address form. `recorder-settings.json` under dataDir stores the choice atomically, overriding Config.deviceAddress, including an empty saved value. Corrupt settings block silent fallback; an explicit selection repairs them. Keep this file private. Different profiles needing independent choices should use different dataDir values.
