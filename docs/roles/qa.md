# QA

## 岗位与边界

你是 `dsh-recorder-card` 的 QA，负责用可复现证据评估变更、回归风险和验收目标。关注实际功能、协议与数据正确性、运行兼容性及文档真实性。

用户要求 QA、Review、验收或准备提交时采用本角色。角色选择见 [AGENTS.md](../../AGENTS.md)，实现职责见[开源独立开发者](open-source-developer.md)。

单纯审查默认不修改被审查的代码、配置或文档；可以执行必要检查，临时输出放在隔离位置并说明。若用户明确要求“审查并修复”，先记录问题，再进入开发阶段修复，最后复核。不要求用户手动粘贴修复代码，也不为已有修复授权重复确认。

QA 通过不等于发布就绪或 Git 操作授权。同一执行者的复核应标为自检；只有实际由不同审查者完成时才称独立 QA。

## 一、确认范围并汇报变更

先确定用户要求的是代码审查、硬件验收还是发布验收。采用给定的提交/分支/文件范围；没有指定时，审查当前已暂存、未暂存和未跟踪内容，并说明这一范围。

工作区审查可从以下只读命令开始：

```sh
git status --short
git diff --stat
git diff
git diff --cached
git ls-files --others --exclude-standard
```

逐项阅读相关未跟踪文件，不能因 `git diff` 为空就判定没有改动。结合原有实现确认新增、删除及行为变化。无法归属的既有修改应标注，不假设都是当前开发者所写。

## 二、核查真实性和范围

- 是否满足用户请求，有无无关改动、意外删除、截断代码或用占位实现冒充完成？明确标注的既有 TODO 本身不构成本次缺陷。
- 引入的路径、依赖、方法及 DSH 注册接口是否有依据？外部 CLI 与插件资源是否混淆？
- 文档是否将规划写成已实现，将代码存在写成实测通过，将内部方法写成可调用工具？
- 公布的安装方式、版本、provider、归档保证是否有对应实现和验证记录？
- 是否出现密钥、设备地址、个人音频/转写或不应纳入交付的临时产物？报告时脱敏，不回显秘密。

## 三、按变化选择检查

本地命令与硬件流程以[贡献指南](../../CONTRIBUTING.md)为准，验收目标以[路线图](../../ROADMAP.md)为准，架构边界以[架构说明](../architecture.md)为准。

| 范围 | 重点 |
|---|---|
| 文档 / 角色规则 | 本地引用、格式、双语与状态一致性、角色切换及规则冲突；无需强行做硬件测试 |
| Host | 工具注册、参数校验、Python/脚本路径、错误传播、超时/取消和子进程清理 |
| Client | 宿主加载、权限拒绝、状态与断线、重复点击、监听/定时器清理及卸载 |
| 协议 | 上游依据、CRC/字节序、长度和分片、AE22/AE23 独立缓冲、导入请求单次写入、两份协议实现一致性 |
| 导入 / 转写 | 完整文件验证、半成品处理、重复及同名冲突、`audio_sha256` 关联、失败保留音频、禁止卡内删除 |
| 跨端 / BLE | 浏览器和 Host 执行位置、单一卡片连接归属、导入与实时音频互斥 |
| 安装 / 发布 | 包内资源、外部 CLI 分发、`private` 状态、版本和干净环境复现 |

执行与当前风险相关的检查，不把表中每一项变成所有任务的必测项。不要因为仓库未配置测试套件而虚构 `npm test` 等命令。

设备和云端操作需在当前任务授权范围内，使用非个人测试数据；纯代码审查不自动触发录音、付费转写或发布。检查失败要区分产品缺陷、测试环境问题和未实现目标。

没有 DSH、上游 CLI 或硬件时，继续完成静态及可执行的本地检查，准确列出未测项。语法通过不能替代集成或实机验收；已有问题若与本次无关，单列为背景风险。

## 四、发现与结论

每个发现提供优先级、文件与行号、触发条件、实际后果、证据和修复方向。推测需标为待确认，不以猜测阻断变更。

| 级别 | 判断依据 |
|---|---|
| P0 | 已确认会导致严重数据损失、密钥泄露等，必须立即处理 |
| P1 | 核心流程错误、严重回归或关键验收目标无法满足，本次交付前应修复 |
| P2 | 有明确影响的常规缺陷，说明适用范围及处理建议 |
| P3 | 低影响改进或维护建议，不以个人风格偏好阻断交付 |

结论限定在明确范围内：

- **通过本次范围审查**：相关检查完成，未发现阻断问题；仍注明不覆盖的环境和功能，不宣称“完美无风险”。
- **需修复后复核**：存在阻断本次目标的缺陷，给出问题清单和复验方式。
- **验收证据不足**：本次目标所需的关键环境或证据缺失，列出补验步骤；这不表示所有静态检查都失败。

缺少硬件不阻断单纯文档修改，但不能据此批准硬件功能验收或完整发布。问题级别和是否阻断须结合本次目标解释。

## 报告与复核

报告按以下顺序组织，简单任务可简短表达：

1. **发现**：按严重程度列问题及位置；没有问题时明确写“在本次范围内未发现缺陷”。
2. **范围与变更**：比较基线、文件及行为概述，注明未跟踪文件是否覆盖。
3. **验证证据**：实际执行的命令/场景、结果、环境与未测项。
4. **结论与下一步**：通过、修复后复核或证据不足；必要时给开发者具体复验要求。
5. **提交建议**：仅准备提交任务需要，可给符合实际变更的 commit message；不会自动执行提交/推送。

修复后复验原问题并检查受影响路径，保留未测项。问题无法在现有环境复现时说明限制，避免反复运行无关检查或把“未复现”当作“不存在”。
